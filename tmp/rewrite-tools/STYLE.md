# 改写规范（Stanford 课程笔记：CS221 / CS229 / CS274 / CS329H）

背景：这些是 Hexo 博客 `source/_posts/` 下的中文课程笔记。现有内容信息密度高、公式与代码多，但“不说人话”：标题像缩写（“## 损失”“## 存在”“## 小步”），段落直接甩定义和结论，缺动机、缺直觉、缺推导中间步骤、缺上下文衔接。目标是改写成一份读者能从头读懂的完整详细笔记。
参考样板：`source/_posts/Stanford-CS230.md`（已按同样要求改写完成，可读其前 300 行感受风格）。

## 一、硬性要求

1. **原内容一条不许少。** 原块里的每个公式、每个数值例子、每个数字结果、每张表、每个代码块、每个链接、每个 callout 中的信息、每条注意事项都必须出现在改写结果里。可以改写措辞、合并重复、调整顺序、移到更合适的小节、改标题，但不能删信息。
   - 代码块原样保留（可在代码里加中文注释；仅当确认原代码有 bug 时修正，并在正文中用一句话说明修正了什么）。
   - 公式保留原式（可以拆成多步、补中间步骤；若确认原式有错，改正并说明）。
   - 原文里的数值（如 `0.1345`、`-0.8361`）必须原样保留。
2. **只写自己负责的那一块**，输出到指定的 part 文件。不要修改仓库里任何其他文件（尤其不要动 `source/_posts/` 下的文件）。
3. **正确性。** 用 WebSearch / WebFetch 检索：课程官网（讲义、slides、syllabus、作业说明）、教材、以及他人的公开笔记（中英文均可，如知乎、CSDN、GitHub 笔记、博客、Stanford 讲义 PDF、cheatsheet）。用它们来（a）核对原笔记的公式与结论，（b）补充直觉解释、推导步骤、例子、常见误区。不要逐字照抄他人文字，用自己的话写。不确定的说法宁可不加。
4. 补充内容要和课程相关、准确，篇幅以“讲清楚”为准。整体长度一般是原块的 1.5–2.5 倍；不要注水，也不要虎头蛇尾——块的后半部分要和前半部分一样细致。

## 二、写法（“说人话”）

每个 `#` 章、每个 `##` 节开头先用 1–3 段白话回答：
- 这一节要解决什么问题、为什么需要它（动机，最好有具体场景/例子）；
- 核心想法一句话是什么（直觉）；
- 和前一节/后一节是什么关系。

然后再给定义、公式、推导、例子、代码。具体要求：
- 符号第一次出现时说明含义和形状/取值范围。
- 推导写出关键中间步骤，每一步说明“为什么能这样做”。
- 结论之后补一句“这意味着什么 / 实际怎么用 / 常见坑”。
- 术语保留中英对照，如“正规方程（normal equations）”，同一术语全文统一。
- 原文的电报体列表（“- **范围** - 输入… 输出…”）改写成通顺的段落或结构清楚的列表；列表项写完整句子。
- 语气客观书面，不用“我们”“你”“我”等人称代词（写成“可以看到”“需要注意”“读者”等无人称表述）。
- 不要写“本节将介绍……”这类空话，开门见山讲动机。

## 三、结构与标题

- `#` = 大章（可沿用原 H1 主题，但标题改为能看懂的完整名称，如 `# 线性回归（Linear Regression）`、`# Bradley–Terry 模型与选择数据`）。
- `##` = 节，`###` = 小节，必要时 `####`。标题要具体、可读（如把“## 存在”改成“## 极大似然解的存在性与唯一性”）。
- 可以重排章内的小节顺序，使逻辑是：动机 → 模型/定义 → 推导/算法 → 例子 → 实现 → 性质/误区/小结。
- 原文中“概念：XXX”式的小节内容融入章首导言即可，不必保留这种标题。
- 每个 `#` 章末尾可加一个简短的 `> [!NOTE]+ 小结`（要点 3–6 条），可选。
- 不要改变自己块之外的章节；块的边界即原 H1 边界。若本块是第一块，必须保留文件开头的 YAML front matter（`---` 到 `---`）原样不动，以及其后的课程信息、版本范围 callout（可改写润色，但信息不少）。

## 四、Markdown / 渲染约定（必须遵守）

- 行内公式 `$...$`，独立公式单独成段：
  ```
  $$
  ...
  $$
  ```
  使用标准 LaTeX（站点已有保护脚本，不需要写 `\_`、`\\\\` 之类的转义；原文里的 `\_` 可以保留也可以改成 `_`）。
- callout 语法：`> [!NOTE]+ 标题`、`> [!EXAMPLE]+ 例1 标题`、`> [!INFO]+ 标题`、`> [!TIP]+ 标题`、`> [!WARNING]+ 标题`。callout 内每一行（含空行、公式行）都以 `>` 开头。callout 不要放进代码块里。
- 大章之间、主要节之间沿用原文的 `<br>` 空行分隔习惯。
- 代码块用 ```python 等标注语言；代码块内部的 `# 注释` 不是标题，不要拿来当标题。
- 表格用标准 GFM 表格。
- 不要使用 HTML 锚点；原文没有站内锚点链接，不必新增。

## 五、工作流程

1. 读 `source/_posts/Stanford-CS230.md` 前 300 行感受目标风格（只读）。
2. 读本块原文（指定的 orig.md 行区间）全部内容；再快速浏览整份 orig.md 的标题（`grep -n '^#'`）了解上下文。
3. 检索课程官网与他人笔记，核对并收集补充材料。
4. 写作：块很长时可分若干临时文件（如 `partNN_a.md`、`partNN_b.md`）写完后用 bash `cat` 拼成 `partNN.md`，再删掉临时文件。
5. 自检：运行
   `python -I tmp/rewrite-tools/check_part.py <orig.md> <起始行> <结束行> <partNN.md>`
   第 1–5 类（代码、display 公式、URL、行内公式、数字）报告为空或每条都能解释（例如公式被改写为等价且更正确的形式）；第 6 类（散文行）逐条确认其信息已在改写中出现。修补到满足为止。
6. 最终回复（给协调者，不给用户看）：简述本块新章节大纲（# / ## 标题列表）、补充了哪些内容、参考了哪些来源（URL）、修正了原文哪些错误、检查脚本最终输出中仍剩下的条目及理由。
